Getting Started / Overview & Philosophy

What is ProGit?

ProGit is an ultra-fast, single-binary, self-hosted Git collaboration platform engineered in pure Go with zero CGO dependencies and an embedded modern React frontend.

Core Mission & Philosophy

ProGit provides development teams and enterprises with an ultra-lightweight, resilient, and beautiful alternative to bloated Git platforms. It runs on any machine with less than 50 MB of RAM, boots in under 50 milliseconds, and operates without external database servers like PostgreSQL or MySQL.

Complete Tutorial Available
New to Git, ProGit, or CI/CD? Check out our dedicated, step-by-step masterclass: Git, ProGit & GitHub Actions CI/CD Tutorial → covering Git internals, staging, branching, conflict resolution, ProGit setup, and 4 production YAML pipeline recipes.
Single Binary Simplicity
Everything — the HTTP REST engine, the Smart Git protocol handler, the built-in SSH server (port 2222), the SQLite WAL database engine, and the production React single-page frontend — is embedded into a single, compact, static binary.

Key Capabilities at a Glance

  • Pure Go & Zero CGO: Cross-compiles instantaneously to Linux, macOS, and Alpine containers without native GCC toolchains.
  • High-Concurrency SQLite WAL: Uses modernc.org/sqlite with Write-Ahead Logging (WAL) and automated checkpoint maintenance.
  • GitHub-Class Developer Experience: Complete with Pull Request line-by-line review comments, native Git merge engine, fork mechanics, and Kanban project boards.
  • Built-in ProGit Pages: Host static websites, documentation, and Jekyll/Markdown sites directly from your repository branches with zero setup.
  • Dual-Interface Wiki Engine: Edit documentation through the web interface or clone and push directly as a Git bare repository (<repo>.wiki.git).
  • In-Browser Code Editor & Prettier: Create files, edit code online, upload entire folder structures, and format with 8 built-in themes.

The Modern Git Service for Teams & Enterprises

ProGit serves as a direct, private, self-hosted replacement for public cloud services like GitHub and GitLab, as well as an upgraded modern alternative to legacy platforms like Gogs and Gitea. It requires zero cloud subscriptions, keeps 100% of your source code and intellectual property on your own infrastructure, and runs seamlessly behind enterprise firewalls or in air-gapped networks.

Deep-Dive: ProGit vs Other Git Services

1. ProGit as a Self-Hosted GitHub Alternative

While GitHub is the industry standard for public open-source hosting, many organizations, defense contractors, healthcare entities, and privacy-conscious teams cannot store proprietary source code on third-party cloud servers. ProGit offers a faithful, modern GitHub-like user experience (React 19 single-page application, dark mode, pull requests, unified syntax-highlighted diffs, Kanban boards, and branch protection) while remaining 100% self-hosted on your own on-premise hardware, private VPC, or air-gapped network.

2. ProGit vs Gogs: The Modernized Successor

Gogs (Go Git Service) proved that a self-hosted Git platform could be fast and lightweight. However, Gogs relies on legacy server-side HTML templates, lacks modern single-page reactivity, does not offer native static site hosting (ProGit Pages), and lacks integrated Git-backed wiki bare repository cloning. ProGit builds upon the proven Gogs architecture, modernizing it with a pure-Go zero-CGO SQLite engine, an embedded React 19 frontend, automated HTTPS, and enterprise OIDC Single Sign-On.

3. ProGit vs Gitea & Forgejo

Gitea and its fork Forgejo originated as forks of Gogs that accumulated significant feature breadth over time. However, this growth introduced operational overhead: larger memory consumption (150-300+ MB idle), complex build pipelines, and hundreds of configuration permutations. ProGit retains a laser focus on high performance, booting in 50ms with less than 40 MB of RAM, embedding all static UI assets into a single executable, and providing first-class rootless Podman and Docker container isolation.

4. ProGit vs GitLab: 100x Lower Resource Requirements

GitLab Community Edition is an all-in-one DevOps platform, but its resource demands are notorious: requiring a minimum of 4 GB to 8 GB of RAM, a dedicated PostgreSQL database, Redis, Puma web server, and Gitaly sidecars. Running GitLab for small-to-medium teams or edge computing environments is frequently cost-prohibitive. ProGit delivers lightning-fast Git hosting, issues, pull requests, wikis, and static pages with less than 1% of GitLab's memory footprint.

Getting Started / Migrating to ProGit

Migrating from GitHub, Gogs, Gitea & GitLab to ProGit

A seamless guide to migrating your Git repositories, branches, tags, and commit histories from any Git service to ProGit.

Seamless Git Mirroring (Recommended)

Because ProGit is fully compliant with the standard Git Smart HTTP and SSH protocols (Git v2), you can mirror any existing repository from GitHub, Gogs, Gitea, or GitLab with zero data loss:

Step 1: Create Target Repository on ProGit

Sign in to your ProGit instance (e.g. https://progit.co.in or your private server) and click + New Repository. Name the repository with the desired owner and slug.

Step 2: Mirror Push from Your Existing Git Service

# 1. Clone a bare mirror of your existing repository from GitHub, Gogs, or Gitea
git clone --mirror https://github.com/your-org/your-repo.git /tmp/mirror-repo
cd /tmp/mirror-repo

# 2. Push all branches, tags, and commit references to ProGit
git push --mirror https://progit.co.in/your-user/your-repo.git

# 3. Clean up temporary mirror clone
cd ~ && rm -rf /tmp/mirror-repo

Step 3: Update Local Developer Workstations

Developers on your team can update their existing Git remotes in one command:

# Update remote URL to point to ProGit
git remote set-url origin https://progit.co.in/your-user/your-repo.git
# Or using SSH:
git remote set-url origin ssh://git@progit.local:2222/your-user/your-repo.git

# Verify remote configuration
git remote -v

Batch Migration for Organizations

If you are migrating dozens or hundreds of repositories from an existing Gogs or Gitea server, ProGit's storage format is standard bare Git (<owner>/<repo>.git). You can copy the bare repository directories directly into ProGit's /data/repositories volume and run the administrative sync command.

5-Minute Quickstart Guide

Get your own private ProGit instance running with Podman or Docker in less than five minutes.

Step 1: Configure Local Domain & Launch Container

Add progit.local to your hosts file and run the official multi-arch image from GitHub Container Registry:

# 1. Map local domain
echo "127.0.0.1 progit.local" | sudo tee -a /etc/hosts
podman run -d --name progit \
  --restart=unless-stopped \
  -p 443:3443 -p 80:3000 \
  -p 3443:3443 -p 3000:3000 \
  -p 2222:2222 \
  -v progit-data:/data/db:Z \
  -v progit-repositories:/data/repositories:Z \
  -v progit-config:/data/config:Z \
  -v progit-logs:/data/logs:Z \
  ghcr.io/sanjeevsenapati/progit:latest
docker run -d --name progit \
  --restart=unless-stopped \
  -p 443:3443 -p 80:3000 \
  -p 3443:3443 -p 3000:3000 \
  -p 2222:2222 \
  -v progit-data:/data/db \
  -v progit-repositories:/data/repositories \
  -v progit-config:/data/config \
  -v progit-logs:/data/logs \
  ghcr.io/sanjeevsenapati/progit:latest

Step 2: Complete Setup Wizard

  1. Open your browser and navigate to https://progit.local (or https://progit.local:3443).
  2. Fill in your desired Super Administrator username, email, and password.
  3. Click Complete Installation & Create Super Admin. ProGit locks the setup and takes you immediately to the dashboard.

Step 3: Create & Push to Your First Repository

# Create test directory and initialize git
mkdir my-project && cd my-project
git init
echo "# Hello ProGit" > README.md
git add README.md
git commit -m "Initial commit"

# Push over Smart HTTP (HTTPS)
git remote add origin https://progit.local/<your-username>/my-project.git
git push -u origin main
SSH Support Out of the Box
You can also push over native SSH at ssh://git@progit.local:2222/<your-username>/my-project.git once you add your public key in User Settings > SSH Keys.

Getting Started / Architecture & Zero CGO

Architecture & Pure Go Engine

Understand how ProGit achieves maximum portability, concurrency, and security with zero CGO dependencies.

Pure Go SQLite WAL Engine

Traditional Git web applications that use SQLite rely on CGO bindings to the C SQLite library (such as mattn/go-sqlite3). This causes several critical operational headaches: slow cross-compilation, reliance on host GCC/Clang toolchains, and complex multi-architecture container setups.

ProGit completely eliminates CGO by using modernc.org/sqlite — a 100% pure Go translation of SQLite. Features include:

  • Zero CGO (CGO_ENABLED=0): Single static Go binary without libc/musl dependency conflicts.
  • Write-Ahead Logging (WAL) Mode: Allows concurrent readers without blocking write transactions.
  • Busy Timeout & Mutex Protections: Configured with 5000ms busy timeout to prevent database is locked errors during high-volume Git pushes.

Podman & Docker Deployment

Deploying ProGit with production-grade container isolation and persistent volumes.

Official Container Images (GHCR)

ProGit publishes official multi-architecture container images to GitHub Container Registry (ghcr.io), verified for Linux x86_64 (AMD64) and ARM64 (Apple Silicon & AWS Graviton):

# Pull the official multi-architecture image (auto-selects amd64 or arm64)
podman pull ghcr.io/sanjeevsenapati/progit:latest
podman pull ghcr.io/sanjeevsenapati/progit:1.6.1

# Or pull platform-specific tags
podman pull ghcr.io/sanjeevsenapati/progit:1.6.1-linux-amd64
podman pull ghcr.io/sanjeevsenapati/progit:1.6.1-linux-arm64

# Run immediately with persistent storage and standard HTTPS / SSH ports
podman run -d --name progit \
  --restart=unless-stopped \
  -p 443:3443 -p 80:3000 \
  -p 3443:3443 -p 3000:3000 \
  -p 2222:2222 \
  -v progit-data:/data/db:Z \
  -v progit-repositories:/data/repositories:Z \
  -v progit-config:/data/config:Z \
  -v progit-logs:/data/logs:Z \
  ghcr.io/sanjeevsenapati/progit:latest

Automated Multi-Arch Build Scripts

ProGit includes dedicated scripts for one-click multi-architecture building and deployment using Podman or Docker:

# Build multi-architecture image manifest (amd64 + arm64)
./podman/build.sh all

# Build native Linux x86_64 on Mac and export standalone progit-linux-amd64.tar
./podman/build.sh amd64 --save

# Deploy container with persistent volumes and healthcheck validation
./podman/deploy.sh ghcr.io/sanjeevsenapati/progit:latest

Manual RHEL 9 / Rocky Linux 9 Installation Process

For enterprise Red Hat Enterprise Linux 9 (RHEL 9), Rocky Linux 9, or AlmaLinux 9 environments, follow this manual step-by-step procedure:

1. Verify Server Architecture

Ensure you pull the container matching your server's CPU architecture:

# Check host architecture
uname -m
# If output is 'x86_64': use ghcr.io/sanjeevsenapati/progit:1.6.1-linux-amd64
# If output is 'aarch64': use ghcr.io/sanjeevsenapati/progit:1.6.1-linux-arm64
Architecture Mismatch Warning

Running an ARM64 image on an x86_64 CPU produces an immediate exec format error crash. On x86_64 servers, pull 1.6.1-linux-amd64 or the multi-arch tag 1.6.1.

2. Configure Firewalld Ports

sudo firewall-cmd --permanent --add-port=3443/tcp --add-port=3000/tcp --add-port=2222/tcp
sudo firewall-cmd --reload

3. Create Volumes & Run Container with SELinux (:Z)

On RHEL 9, SELinux runs in Enforcing mode. The :Z flag assigns the container_file_t context to prevent permission denied errors on SQLite and Git repositories:

# Create named volumes
podman volume create progit-data
podman volume create progit-repositories
podman volume create progit-config
podman volume create progit-logs

# Launch container manually
podman run -d \
  --name progit \
  --restart=unless-stopped \
  -p 3443:3443 \
  -p 3000:3000 \
  -p 2222:2222 \
  -v progit-data:/data/db:Z \
  -v progit-repositories:/data/repositories:Z \
  -v progit-config:/data/config:Z \
  -v progit-logs:/data/logs:Z \
  ghcr.io/sanjeevsenapati/progit:1.6.1-linux-amd64

4. Enable Systemd Auto-Start on Boot

# Enable lingering for rootless user
loginctl enable-linger $USER

# Generate and enable systemd service unit
mkdir -p ~/.config/systemd/user/
podman generate systemd --name progit --files --new
mv container-progit.service ~/.config/systemd/user/
systemctl --user daemon-reload
systemctl --user enable --now container-progit.service

Installation / Standalone Binary

Standalone Binary Installation

Run ProGit directly on Linux or macOS as a native system daemon without containers.

1. Create System User and Directories

sudo adduser --system --shell /bin/bash --gecos 'ProGit Version Control' --group --disabled-password --home /home/git git
sudo mkdir -p /data/db /data/repositories /data/config /data/logs
sudo chown -R git:git /data

2. Place Binary

sudo cp progit /usr/local/bin/progit
sudo chmod +x /usr/local/bin/progit

3. Systemd Service File

Create /etc/systemd/system/progit.service:

[Unit]
Description=ProGit Service
After=syslog.target
After=network.target

[Service]
Type=simple
User=git
Group=git
WorkingDirectory=/data
ExecStart=/usr/local/bin/progit web
Restart=always
Environment=PROGIT_APP_NAME="ProGit"

[Install]
WantedBy=multi-user.target

Enable and start the service:

sudo systemctl daemon-reload
sudo systemctl enable --now progit

Installation / HTTPS & TLS

HTTPS & TLS Configuration

Securing Git traffic with automatic TLS, HSTS, and custom certificates.

Built-in HTTPS Server (Default in v1.3.0)

ProGit features a native, pure-Go HTTPS engine that runs out of the box with zero external dependencies. In conf/app.ini or container environment:

[server]
PROTOCOL = https
DOMAIN = progit.local
ROOT_URL = https://progit.local:3443/
HTTP_PORT = 3000
HTTPS_PORT = 3443
REDIRECT_OTHER_PORT = true
CERT_FILE = /data/config/https/cert.pem
KEY_FILE = /data/config/https/key.pem

Automatic Self-Signed Certificates & SANs

ProGit automatically generates an ECDSA P-256 self-signed certificate on initial boot if no certificate exists. The certificate includes full Subject Alternative Names (SANs) for:

  • progit.local & *.progit.local
  • localhost & *.localhost
  • 127.0.0.1 & ::1
  • Local machine hostnames and discovered interface IPs

Certificates are saved persistently in /data/config/https/cert.pem and automatically renewed if the domain name changes in the Admin Settings.

Seamless HTTP to HTTPS Redirection

When REDIRECT_OTHER_PORT = true, ProGit starts an HTTP redirect listener on port 3000 (or 80) that automatically redirects all incoming browser traffic with 301 Moved Permanently directly to https://progit.local/. Health check probes to /api/health respond with 200 OK immediately on both ports without redirection latency.

Installation / Reverse Proxy

Reverse Proxy Setup

Configuring Nginx or Caddy in front of ProGit for SSL termination and custom domains.

Nginx Configuration

server {
    listen 80;
    server_name git.example.com;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl http2;
    server_name git.example.com;

    ssl_certificate /etc/letsencrypt/live/git.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/git.example.com/privkey.pem;

    client_max_body_size 500M;

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}

Caddy Configuration

git.example.com {
    reverse_proxy 127.0.0.1:3000
    request_body {
        max_size 500MB
    }
}

Webhooks & Automated Delivery

Trigger CI/CD pipelines, Slack/Discord notifications, and custom webhooks automatically on Git push, issue, and pull request events.

Overview

ProGit features an asynchronous, pure-Go webhook dispatch engine. When events occur in your repository (such as code pushes over HTTP or native SSH, issue creation, or pull request reviews), ProGit queues and delivers HTTP POST payloads with cryptographic HMAC signatures to your subscribed endpoints.

Supported Event Triggers

EventTrigger ConditionPayload Contents
pushCode committed or branch pushed via Git CLI (Smart HTTP / SSH) or online file editorRepository metadata, pusher account, Git ref, before/after commit SHAs, commit array
issuesIssue opened, closed, edited, or assigned to a collaboratorRepository info, issue title, issue body, sender, state

Cryptographic Signature Verification (HMAC-SHA256)

When you configure a secret token on a webhook, ProGit calculates a cryptographic HMAC-SHA256 signature for every payload and transmits it in both standard GitHub-compatible and ProGit headers:

  • X-Hub-Signature-256: sha256=<hex-encoded HMAC signature>
  • X-ProGit-Signature: sha256=<hex-encoded HMAC signature>
  • X-ProGit-Event: The event name (e.g. push, issues, pull_request, ping)
  • X-ProGit-Delivery: Unique delivery UUID for tracing and idempotency
Verifying Signatures in Python

You can verify webhook requests in your backend using standard HMAC routines:

import hmac, hashlib

def verify_progit_signature(payload_bytes, secret_key, header_signature):
    expected = "sha256=" + hmac.new(secret_key.encode(), payload_bytes, hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, header_signature)

Delivery Logs & Test Pings

Repository administrators can trigger an immediate test ping from the Repository Settings → Webhooks tab to verify network connectivity and signature verification. Each delivery is logged with full request/response diagnostics, HTTP status codes, and execution duration.

Enterprise / Multi-Node HA & Business Model

ProGit Enterprise: Multi-Node High Availability & Commercial Strategy

Architecture blueprint for multi-node clustering, disaster recovery, target market fit, and commercial monetization.

Executive Summary

ProGit has evolved into a high-performance, single-binary enterprise Git platform with low resource consumption, an embedded React interface, full SSH/HTTPS Git mechanics, and zero external runtime dependencies.

While the single-node architecture delivers industry-leading simplicity (< 100 MB RAM, sub-second startup), mid-market IT firms and enterprise engineering teams require Multi-Node High Availability (HA) to eliminate single points of failure (SPOF), achieve 99.99% service level agreements (SLAs), and support disaster recovery (DR). Furthermore, enterprise Dev/QA environments often require independent, air-gapped, or ephemeral staging Git clusters where per-seat pricing models from GitHub Enterprise ($21/user/mo) or GitLab Ultimate ($99/user/mo) are cost-prohibitive.

Key Architectural Objectives
Deliver active-active clustering, zero-downtime rolling upgrades, sub-second RPO, and a developer-friendly commercial pricing model (~40% to 80% savings vs. legacy platforms).

Multi-Node High Availability (HA) Architecture

A scalable, resilient ProGit HA cluster splits concerns into four distinct tiers:

  1. Edge Routing & Ingress Tier: High-availability load balancers (HAProxy / Cloud NLB) routing HTTPS and Git SSH traffic.
  2. Stateless Compute Tier (progit-core): Multiple application instances serving API, Web UI, and orchestrating Git operations.
  3. Clustered Metadata & Cache Tier: Multi-master or primary-replica PostgreSQL with Redis/Dragonfly for distributed locks and cache.
  4. Resilient Git Storage Tier (progit-storage): Replicated block storage or dedicated gRPC-based storage nodes.

Component Breakdown & HA Mechanics

A. Ingress & Load Balancing

  • HTTPS Traffic (Port 443 / 3000): Terminated at cloud load balancers or HAProxy. Continuous health probing against GET /healthz verifies database and storage health.
  • Git SSH Traffic (Port 22 / 2222): Layer-4 TCP balancing with PROXY protocol v2 to preserve client IP addresses in audit logs. Compute nodes share synchronized SSH Host Keys mounted via shared secrets to eliminate client host key mismatch warnings.

B. Stateless Compute Nodes (progit-core)

  • Application instances maintain zero local disk state.
  • User authentication tokens (JWT) are signed with asymmetric ECDSA keys.
  • Repository write locking and brute-force protection are coordinated via Redis.

C. Clustered Database Backend

  • Pluggable Store: Abstract database access to support SQLite (single-node) and PostgreSQL (clustered HA).
  • Patroni + PgBouncer: Primary PostgreSQL handles writes; read replicas handle heavy browsing queries. Automatic failover occurs in < 10 seconds.
  • Air-Gapped Embedded Option: LiteFS or rqlite (distributed SQLite over Raft) for edge environments desiring zero external DBMS dependencies.
